## Purpose

This is the living technical reference for the Group 23 Robocup project. It records what is implemented, how data moves between modules, the current wiring assumptions, what has been verified on hardware, and what is still incomplete. Update it whenever wiring, addresses, task periods, protocol fields, or subsystem status changes.

The project currently has a working modular sensor and debug foundation. The Teensy firmware builds successfully, the Python tools compile, most sensor drivers have been integrated, and live telemetry can be transported as newline-delimited JSON. Manual main-drive control is implemented with a safety watchdog and keyboard control; autonomous behaviour and closed-loop speed control are still incomplete. Several hardware paths also need revalidation, especially the shared `Wire1` bus and the wheel encoders.

### Firmware startup flow

`setup()` in `src/main.cpp` performs the following sequence:

1. Starts USB `Serial` and the CH9143 Bluetooth bridge on `Serial1` at 115200 baud.
2. Enables board IO power by driving Teensy pin 49 high.
3. Initializes the distance-sensor subsystem. This starts both I2C buses, initializes the SX1509, registers the enabled distance sensors, holds all VL53 devices in reset, then releases and assigns them one at a time. The serial TOF is disabled because Serial2 is allocated to drive PWM.
4. Initializes the TCS34725 colour sensor on `Wire1`.
5. Initializes the PMW3901 optical-flow sensor on SPI.
6. Initializes the BNO055 IMU on `Wire1`.
7. Initializes the inductive sensor, encoder interrupts, test servo outputs, and both main-drive outputs at neutral.
8. Starts the dual USB/Serial1 line console and JSON protocol. JSON-looking lines from either transport are routed from Console to DebugProtocol.
9. Adds and enables the active scheduler tasks.

Initialization failures are reported, but setup continues so that one missing sensor does not stop the rest of the robot. Sensor wrappers that failed initialization avoid blocking reads and remain invalid.

### Distance sensor interface

All range sensors implement `DistanceSensor`:

```cpp
bool begin();
void preReset();
void update();
uint16_t getDistanceMM() const;
bool isValid() const;
const char* getName() const;
```

`SensorManager` stores up to 16 `DistanceSensor` pointers. The current configuration registers 12: seven VL53 sensors, one 8x8 array, and four IR sensors. The serial TOF is disabled to free Serial2 for the drive ESCs, and ultrasonic support is disabled because D30--D33 are assigned to encoders.

The public access points are in `DistanceSensors.h`:

- `distance_sensor_get(name)` returns one sensor by its registered name.
- `distance_sensor_get_by_index(index)` supports generic iteration.
- `distance_sensors_update()` refreshes all registered sensors.
- `distance_sensors_8x8_min_mm()` returns the closest valid 8x8 zone.

The 8x8 array is special: the generic interface exposes its near-centre zone, while `MatrixLidarSensor::getGrid()` and `distance_sensors_get_8x8_grid()` expose all 64 zones. The JSON protocol publishes every zone independently for the GUI heat map and plotting.

### Other sensor interfaces

Non-distance hardware uses a similar wrapper plus a small subsystem facade:

- `ImuSensor` -> `IMU.cpp` -> heading, pitch, roll and calibration getters
- `OpticalFlowSensor` -> `OpticalFlow.cpp` -> delta and accumulated counts
- `InductiveSensor` -> `Inductive.cpp` -> debounced active-low detection and count
- `EncoderSensor` -> `Encoders.cpp` -> interrupt-updated positions and reset
- `ColourSensor` -> `sensors.cpp` -> raw red, green, blue and clear channels
- `ServoControl.cpp` -> pulse, speed and angle commands
- `DriveControl.cpp` -> left/right main-drive percent and PWM pulse getters

The wrappers cache values. Other code should use the facade getters rather than talk to vendor libraries directly.

## Wiring and address map

### Buses

| Bus | Teensy pins | Device | Address or select | Notes |
|---|---:|---|---:|---|
| `Wire` I2C bus 0 | SDA 18, SCL 19 | SX1509 IO expander | `0x3F` | Controls all seven VL53 XSHUT lines |
| `Wire` I2C bus 0 | SDA 18, SCL 19 | 2 x VL53L0X | `0x30`, `0x31` | Addresses assigned at startup |
| `Wire` I2C bus 0 | SDA 18, SCL 19 | 5 x VL53L1X | `0x35` to `0x39` | Addresses assigned at startup |
| `Wire1` I2C bus 1 | SDA 17, SCL 16 | BNO055 | `0x28` | IMU part of SEN0253 |
| `Wire1` I2C bus 1 | SDA 17, SCL 16 | TCS34725 | `0x29` | Raw RGBC colour sensor |
| `Wire1` I2C bus 1 | SDA 17, SCL 16 | DFRobot 8x8 TOF | `0x33` | 64-zone matrix sensor |
| SPI | MOSI 11, MISO 12, SCK 13 | PMW3901 | CS 10 | Optical-flow counts, not millimetres |
| `Serial1` | RX1 D0, TX1 D1 | CH9143 Bluetooth bridge | 115200 baud | Same app telemetry and commands as USB; UART TX/RX cross at the module |
| `Serial2` connector | RX2 D7, TX2 D8 | Main-drive ESC PWM | 1050/1500/1950 us | Serial ToF disabled: these pins cannot share UART and PWM |
| USB `Serial` | USB cable | Debug GUI and text console | 115200 selected in app | JSON and text are mutually exclusive modes |

`Wire` runs at 400 kHz. `Wire1` is currently set to 100 kHz by `distance_sensors_init()` for conservative 8x8 operation; the colour and IMU modules reuse the already-started bus.

### GPIO and analog connections

| Function | Pin or pins | Current use |
|---|---:|---|
| Board IO power enable | D49 | Driven high during startup |
| IR distance 0 to 3 | A6, A7, A8, A9 | Analog readings converted to approximate millimetres |
| Inductive proximity | A0, also D14 | Digital active-low input with 10 ms debounce |
| Ultrasonic 0 and 1 | Formerly D30–D33 | **Disabled:** pins reassigned to encoders |
| Encoder 0 | D30 channel A, D31 channel B | Full A/B interrupt quadrature decode |
| Encoder 1 | D32 channel A, D33 channel B | Full A/B interrupt quadrature decode |
| Main drive left | D7 / RX2 | PWM output is direction-reversed in configuration so positive app command means physical forward |
| Main drive right | D8 / TX2 | PWM output is direction-reversed in configuration so positive app command means physical forward |
| Servo test connector | D28 and D29 | Both currently output the same command |

D28 and D29 are also the `Serial7` pins. They cannot be used for `Serial7` while attached as servo PWM outputs. Both are deliberately driven because the physical signal conductor has not yet been identified; this is a temporary test arrangement.

### VL53 XSHUT mapping

The XSHUT numbers are SX1509 IO numbers, not Teensy GPIO numbers.

| Physical label | SX1509 IO | Sensor type | Runtime I2C address | Registered name |
|---|---:|---|---:|---|
| XSHUT0 | IO0 | VL53L0X | `0x30` | `tof_xshut0` |
| XSHUT1 | IO1 | VL53L0X | `0x31` | `tof_xshut1` |
| XSHUT2 | IO2 | VL53L1X | `0x35` | `tof_xshut2` |
| XSHUT3 | IO3 | VL53L1X | `0x36` | `tof_xshut3` |
| XSHUT4 | IO4 | VL53L1X | `0x37` | `tof_xshut4` |
| XSHUT5 | IO5 | VL53L1X | `0x38` | `tof_xshut5` |
| XSHUT6 | IO6 | VL53L1X | `0x39` | `tof_xshut6` |

At boot, `SensorManager::beginAll()` first drives every XSHUT low. It then starts the sensors in registration order, changes each from the shared factory address `0x29`, and only then releases the next sensor.

## Scheduler and timing

The project uses a cooperative scheduler. Long blocking calls delay every other task.

| Active task | Period | Behaviour |
|---|---:|---|
| Distance sensor update | 20 ms | Calls every registered distance sensor; the 8x8 wrapper limits hardware requests to 100 ms and bounds missing responses to 150 ms |
| Colour sensor update | 60 ms | Performs a blocking TCS34725 raw read with approximately 50 ms integration |
| Optical-flow update | 20 ms | Reads new motion counts |
| IMU update | 20 ms | Reads Euler orientation and calibration |
| Inductive update | 20 ms | Runs debounce state machine |
| Console update | 20 ms | Non-blocking line collection and dispatch |
| Debug protocol poll | 10 ms | Sends JSON telemetry on the selected USB or Bluetooth transport; sends nothing unsolicited on Serial1 |
| Normal sensor print tasks | 1000 ms | Human-readable debugging |
| 8x8 grid print | 3000 ms | Prints all 64 millimetre values |

The telemetry interval is separately tunable from 20 to 2000 ms and defaults to 100 ms, or 10 Hz. USB CDC has sufficient headroom for the 64-zone frame. Changing print frequency does not change sensor sampling frequency.

Motor, weight collection, return-to-base, base detection, unloading, generic averaging, and the old `read_ultrasonic` and `read_infrared` placeholder tasks are not added to the scheduler. The real IR and ultrasonic classes are already updated by the distance-sensor task; the placeholder tasks should not be enabled.

## Serial links and commands

The firmware accepts the same human-readable commands and JSON application protocol from USB `Serial` and the CH9143 on `Serial1`. `Console.cpp` maintains an independent line buffer for each. `DebugProtocol` sends replies and telemetry through whichever transport most recently sent JSON. When JSON mode becomes active, human-readable print tasks are suppressed so they cannot corrupt JSON. Hardware `Serial2` is used as D7/D8 PWM drive output, not as a UART.

### Human-readable mode

USB human-readable output is the startup mode. Available console commands are:

```text
mode sensors
mode test
servo us 500-2500
servo speed -100..100
servo angle 0-180
servo stop
drive <left> <right>
drive stop
help
```

`mode test` hides sensor print tasks while leaving sensor updates active. `SERIAL_PRINT_PERIOD` in `src/main.cpp` is the main print-rate setting and currently equals 1000 ms.

### JSON debug mode

When the Python GUI sends `{"type":"hello"}` over USB, the firmware starts newline-delimited JSON telemetry and disables human-readable sensor print tasks on that same stream.

The actual telemetry names produced by the current firmware are:

- `tof.xshut0` through `tof.xshut6`
- `tof.8x8` for the near-centre matrix zone when valid
- `tof.array_min` for the closest valid matrix zone
- `tof.array.r0c0` through `tof.array.r7c7` for all 64 matrix zones
- `tof.array_valid_zones` for frame health
- `ir.0` through `ir.3`
- `ultrasonic.0` and `ultrasonic.1`
- `colour.r`, `colour.g`, `colour.b`, `colour.c`
- `imu.heading`, `imu.roll`, `imu.pitch`
- `imu.cal_system`, `imu.cal_gyro`, `imu.cal_accel`, `imu.cal_mag`
- `flow.dx`, `flow.dy`, `flow.total_x`, `flow.total_y`
- `inductive.detected`, `inductive.count`
- `encoder.0`, `encoder.1`
- `servo.us`
- `drive.left_percent`, `drive.right_percent`, `drive.left_us`, `drive.right_us`, `drive.active`
- `bluetooth.active`, `bluetooth.rx_messages`
- `system.uptime_ms`

Every signal is sent each packet. Invalid readings are JSON `null`, which clears stale GUI values and displays as `INVALID`. The full 64-zone grid is sent to the dedicated 8x8 GUI view; every zone can also be plotted and recorded. `telemetry_definition` messages provide labels, groups, units and plotting metadata.

The firmware advertises three parameters:

- `telemetry.interval_ms`, constrained to 20 to 2000 ms
- `servo.pulse_us`, advertised as 1000 to 2000 us and gated by debug mode
- `drive.max_percent`, gated by debug mode and hard-capped at 100 percent

It advertises six commands:

- `stop`, always allowed and neutralizes every actuator output
- `set_debug_mode`
- `servo_set`, gated by debug mode
- `drive_set`, gated by debug mode; accepts independent `left` and `right` percentages
- `encoders_reset`
- `set_text_mode`

The low-level servo function permits 500 to 2500 us, while the GUI parameter definition advertises the safer 1000 to 2000 us range.

## Python application data flow

`BluetoothSerial.py` owns a generic `QThread` serial worker. It opens either the direct Teensy USB port or the computer-side CH9143 virtual serial port with `pyserial`, accumulates partial reads until a complete newline, emits raw text for inspection, parses JSON objects, and converts protocol message types into Qt signals. Outgoing lines are paced in 20-byte chunks for CH9143 reliability.

On connection it sends:

1. `hello`
2. `request_definitions`

The firmware then advertises its parameters and commands. `DebugGUI.py` builds controls from those definitions, so adding a compatible firmware parameter or command normally does not require a Python UI change.

For grouped telemetry, `BluetoothSerial.py` emits one Qt signal per key in the JSON `data` object. `DebugGUI.py` stores the latest value, appends numeric history for plots, updates the grouped/unit-labelled telemetry table, updates the 8x8 heat map, and optionally records the sample. Numeric signals are automatically available to the plotter; a matrix cell can be selected and plotted directly.

`DataRecorder.py` writes `.rdbg` SQLite files on a background thread. The schema contains metadata, telemetry, logs, commands, parameter edits and snapshots, robot states, raw serial lines, faults, and annotations. Files are stored under `tools/debug_gui/Data/` and ignored by Git.

`DataVisualiser.py` loads recordings for plots, event inspection, comparison runs, derived signals, measurement regions, anomaly detection, raw serial inspection, and CSV export. `DataAnalysisCLI.py` provides terminal commands for summaries, statistics, fault context, correlations, PID metrics, anomalies, exports, and Markdown reports.

The active protocol is transport-independent and works over direct Teensy USB `Serial` or the matched CH9143 bridge on `Serial1`. USB remains mandatory for firmware upload; runtime telemetry, plotting, recording, parameters, commands, STOP, and keyboard driving are available through either app connection. Bluetooth uses a minimum 500 ms interval for the large grouped telemetry packet to fit the 115200-baud link reliably.

## Known issues and technical risks

1. **The `Wire1` hardware path needs revalidation.** The 8x8 array, colour sensor and BNO055 share this bus. They worked at different stages, but later the 8x8 became invalid and colour values became zero. A failure affecting all three points first to shared SDA, SCL, power, ground, or connector integrity rather than three independent driver failures.
2. **Ultrasonic sensing is parked.** D30--D33 were reassigned to the encoders, so the ultrasonic feature is disabled in `sensor_config.h`. Reassign non-conflicting pins and re-enable it once its power and echo-voltage issues are resolved.
3. **Encoder counts are not hardware-verified.** Confirm encoder supply, common ground, signal voltage, pin continuity, and whether pull-ups are required. Then observe D30 to D33 with a scope or logic analyser before changing the decoder.
4. **The servo signal pin is still ambiguous.** Driving both D28 and D29 works for testing but consumes two pins and prevents `Serial7` use. Identify the actual signal conductor and drive only that pin.
5. **The serial TOF is intentionally offline.** Its D7/D8 Serial2 connector now carries PWM to the main-drive ESCs. Do not re-enable `SERIAL_TOF_ENABLED` unless the drive motors are moved to different pins.
6. **The colour read blocks the cooperative scheduler.** Its approximately 50 ms integration call runs every 60 ms, so nominal 20 ms tasks cannot maintain their requested timing. Consider a non-blocking register read strategy or reduce the read rate when timing becomes important.
7. **USB passed the automated live protocol suite on 22 September 2026.** It received 112 signal definitions, six commands, 64 telemetry packets, parameter round-trips, state and safe zero-speed commands. The CH9143 port opened but returned no bytes, and USB telemetry reported `bluetooth.rx_messages = 0`. Check robot-side radio power/pairing and crossed wiring: robot-module TX to Teensy RX1 D0, robot-module RX to Teensy TX1 D1.
8. **Unsolicited Serial1 output is deliberately disabled.** A startup beacon could stall the cooperative scheduler when the radio path was unavailable. Bluetooth transmits only after receiving the app's `hello`, so an absent radio cannot stall sensors, STOP handling, or USB telemetry.
9. **Documentation naming is slightly inconsistent.** The actual centre-zone telemetry key is `tof.8x8`; older GUI documentation refers to `tof.array_centre`.
10. **Robot behaviour modules are still inherited stubs.** Do not mistake successful compilation for autonomous readiness.

## Recommended next integration order

1. Recheck board IO power, ground, and both I2C buses with an address scanner.
2. Revalidate all three `Wire1` devices together at `0x28`, `0x29`, and `0x33`.
3. Identify the single servo signal pin and stop driving the other pin.
4. Prove encoder waveforms electrically, then verify signed counts and counts per wheel revolution.
5. Restore HC-SR04 power and echo operation, then stagger trigger timing.
6. Connect and verify the USB GUI handshake, telemetry definitions, live values, 8x8 view, plots, recording, commands and emergency stop path.
7. Test the drive motors with wheels clear of the ground: start at 5 percent, check left/right orientation, then verify the timeout and STOP paths.
8. Add closed-loop wheel-speed tests before writing autonomous behaviour.
9. Move the serial TOF to a free UART if it is required, then re-enable and test it.
10. Implement navigation, weight collection, return-to-base and unloading as explicit state machines.

## How to add another sensor

For another distance sensor:

1. Add pins, bus and address to `include/sensor_config.h`.
2. Implement a `DistanceSensor` subclass under `include/sensors` and `src/sensors`.
3. Construct and register it in `src/DistanceSensors.cpp`.
4. Keep `update()` non-blocking where practical and cache the latest reading.
5. Return `false` from `isValid()` for timeouts, sentinel values, failed initialization or absent targets.
6. The generic JSON loop will automatically publish the sensor using its registered name, including `null` when invalid. Add a telemetry definition if a friendlier label or non-mm unit is required.

For a non-distance sensor:

1. Create a small hardware wrapper that owns the vendor object and cached data.
2. Add a subsystem facade with `init`, `update`, validity and getter functions.
3. Initialize it in `setup()`.
4. Add an appropriately paced scheduler task.
5. Add telemetry fields in `debug_protocol_send_telemetry()`.
6. If it needs tuning or test actions, advertise parameter and command definitions rather than hard-coding GUI controls.

## Build and operation reference

From the repository root:

```bash
platformio run
platformio run -t upload
platformio device monitor
```

The USB monitor and Python GUI both use the Teensy's USB serial port at 115200. They cannot run at the same time: close PlatformIO's monitor before connecting the GUI, and disconnect the GUI before reopening the monitor.

To run the Python tools:

```bash
cd tools/debug_gui
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python DebugGUI.py
```

Offline tools:

```bash
python DataVisualiser.py
python DataAnalysisCLI.py summary Data/SomeRun.rdbg
```

If PyQt reports that the macOS `cocoa` platform plugin cannot be initialized, reinstall the Qt wheel in the active virtual environment:

```bash
pip install --force-reinstall --no-cache-dir "PyQt6==6.11.0" "PyQt6-Qt6==6.11.0"
```

## Update checklist

When the project changes, update this document if any of these changed: a physical pin or connector; an I2C address or bus; a sensor model or quantity; a scheduler period; a telemetry key, parameter, or command; a confirmed hardware status; an unresolved fault; a build result; or a module implementation status.

Keep observed hardware results separate from code completion. A driver can compile without the wiring being correct, and a sensor can work electrically without its data yet being useful to the robot.
